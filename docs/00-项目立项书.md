# recon-ai 项目立项书

> 版本 v1.0 ｜ 2026-11-16 ｜ 作者：肖俊辉
> 用途：个人作品项目，同时作为「需求 → 设计 → 编码 → 测试 → 上线」完整生命周期的实践样本

---

## 1. 背景与场景

### 1.1 行业背景

K12 教育缴费 SaaS：家长通过微信/支付宝缴纳学费、餐费、校服费等。资金不直接进入学校账户，而是经由支付机构结算，**T+1 出具对账单**。学校财务必须每天核对「渠道记录」与「系统订单」，确认钱账一致。

### 1.2 业务场景

某民办学校，2,140 名学生，秋季开学集中缴费。财务每天上午需要完成前一日流水的对账：

1. 从微信/支付宝商户后台下载对账文件（CSV）；
2. 从业务系统导出订单流水（CSV）；
3. 两份文件逐笔比对，找出「渠道有、系统无」「系统有、渠道无」「金额不一致」的记录；
4. 为每条差异写明原因，交主管确认；
5. 差异处置后归档，等待月度审计。

### 1.3 现状与痛点（量化）

| 痛点 | 现状数据 |
|---|---|
| 纯手工比对 | 每天 2~2.5 小时，开学季峰值 4 小时 |
| 归因靠经验 | 新人上手 2 周；同类问题每月重复出现 |
| 无沉淀 | 处置结论留在个人 Excel 里，无法复用 |
| 不可审计 | 审计问「这条差异当时为什么这么判」，答不出来 |
| 易错 | 2,000 行 VLOOKUP，漏行、错行无法自查 |

### 1.4 价值假设（项目要验证的）

- 对账耗时从 2.5 小时降到 **15 分钟以内**；
- 每条差异有**可解释的归因**（分类 + 理由 + 依据 + 置信度）；
- 人工纠正被记录，**同类差异的处理结论可复用**；
- 全流程留痕，任何一条差异可追溯到「谁、何时、依据什么」处理的。

## 2. 用户

### 2.1 用户画像

| 角色 | 描述 | 关注点 | 使用频率 |
|---|---|---|---|
| **主：财务对账专员**（小张，28 岁） | 非技术背景，Excel 熟练，负责日常对账 | 快、准、能解释 | 每天 1 次 |
| 次：财务主管（王姐，38 岁） | 审批差异处置，月度对审计 | 可追溯、有报表 | 每周 1~2 次 |
| 系统：运维/开发 | 处理失败任务 | 日志、重跑 | 按需 |

**本项目的设计重心是「小张」**——她不会写 SQL，看不懂技术术语，只关心「这条差在哪、为什么、我该怎么做」。

### 2.2 As-Is（现在的做法）

```
09:00 下载渠道 CSV
09:05 导出系统订单 CSV
09:10 打开 Excel，VLOOKUP 比对
09:30 找到 30~50 条差异
09:40 逐条猜原因（跨日？手续费？退款？）
11:30 整理成说明文档，发主管
```

### 2.3 To-Be（用了系统之后）

```
09:00 上传两个 CSV
09:00:10 系统给出 37 条差异，已分类
09:02 逐条看 AI 归因，确认或纠正
09:15 导出报告，发给主管
```

## 3. 需求

### 3.1 范围边界

**做什么（In Scope）**

- 渠道账单与系统订单的**核对**
- 差异的**识别、分类、解释、处置、留痕**
- 归因结果的**沉淀与复用**

**不做什么（Out of Scope，写进文档防跑偏）**

- ❌ 不做支付、退款、记账（那是 pay-service 的事）
- ❌ 不做多租户、多学校（单租户）
- ❌ 不做实时对账（只做 T+1 批量）
- ❌ 不做自动修复账务（只给建议，人确认）

### 3.2 用户故事与验收标准

| ID | 用户故事 | 验收标准 |
|---|---|---|
| **US-1** | 作为对账专员，我上传两份 CSV，希望系统自动找出差异 | 上传后 10s 内出结果；格式错误时提示**具体行号与原因** |
| **US-2** | 作为对账专员，我想看到差异清单并按类型筛选 | 列表分页；可按分类/状态筛选；显示总数与金额合计 |
| **US-3** | 作为对账专员，我点开一条差异，想看到两侧原始记录和匹配过程 | 展示渠道行、系统行、匹配规则（精确/模糊/未匹配） |
| **US-4** | 作为对账专员，我希望系统告诉我**为什么**差、**该怎么做** | 输出分类（6 类之一）+ 理由 + 依据 + 置信度 + 建议动作 |
| **US-5** | 作为对账专员，AI 判错时我能纠正 | 纠正后写入反馈表，列表标记「已纠正」 |
| **US-6** | 作为主管，我想看这次对账的汇总 | 总数、差异数、金额差、分类分布 |
| **US-7**（P1） | 作为对账专员，我想导出差异报告 | 导出 CSV，字段与页面一致 |

### 3.3 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 2,000 行对账 ≤ 10s；列表首屏 ≤ 500ms；单次 AI 调用 ≤ 10s |
| 可用性 | **AI 不可用时，对账主流程仍完整可用**（降级为规则分类） |
| 成本 | 单次对账 AI 调用 ≤ 50 次；每次调用记录 token 与耗时 |
| 可观测 | 每个任务一个 trace_id，贯穿 3 个服务；失败可定位到具体环节 |
| 安全 | 文件仅内网可传；金额只读；所有处置动作留审计日志 |
| 数据 | 原始文件保留 30 天可回溯；差异数据不可物理删除 |

### 3.4 成功指标（项目验收）

- 分类准确率 ≥ 85%（30 条标注集）
- 端到端耗时 ≤ 15s（2,000 行）
- AI 降级后主流程可用率 100%
- 从上传到导出一份报告，操作 ≤ 5 次点击

## 4. 概要设计

### 4.1 架构

```
React(Vite) ──HTTP──> recon-bff ──gRPC──> recon-core ──> Postgres
                          │
                          └────gRPC──> recon-ai ──HTTPS──> LLM
```

### 4.2 服务划分

| 服务 | 协议 | 存储 | 职责 | 不做什么 |
|---|---|---|---|---|
| **recon-bff** | HTTP | 无 | 对外 API、鉴权、上传、聚合、SSE | 不碰 DB、不写业务规则 |
| **recon-core** | gRPC | Postgres | 任务、记录、匹配、差异、确认、审计 | 不调 LLM |
| **recon-ai** | gRPC | 无 | prompt、模型调用、结构校验、降级、计量 | 不碰业务库 |

**依赖方向**：`bff → core`、`bff → ai`；core 与 ai 互不依赖。

### 4.3 关键选型（ADR）

| 决策 | 选择 | 理由 | 放弃的方案 |
|---|---|---|---|
| 后端框架 | Kratos | 三服务需 gRPC + 服务发现 + 统一错误码；与既有经验一致 | Gin（单体够用，但表达不出服务治理） |
| 服务数 | 3 | 正好表达 BFF / 核心 / AI 三种职责，再多是过度设计 | 2 个（AI 逻辑混进 core，降级不干净） |
| 调模型语言 | Go | 单二进制、与主服务同栈、便于统一限流 | Python（生态好，但多一套运行时与部署） |
| AI 位置 | 独立服务，core 不依赖 | 模型慢且会挂，不能绑架核心链路 | core 内联调用（一处故障全站不可用） |
| 通信 | gRPC + proto | 契约先行、强类型、代码生成 | HTTP JSON（弱类型，改字段易漏） |
| 前端 | Vite + React | 轻、快、生态成熟 | Next.js（SSR 对本项目无收益） |

## 5. 详细设计

### 5.1 数据模型（4 张表）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `recon_task` | id, name, status, total_count, diff_count, diff_amount, created_at | 一次对账 |
| `recon_record` | id, task_id, source(1渠道/2系统), trade_no, biz_no, amount, fee, trade_time, status | 两类账单合并，`source` 区分 |
| `recon_diff` | id, task_id, channel_record_id, system_record_id, diff_type, amount_diff, category, confidence, reason, evidence, state, ai_model, prompt_version | 差异 |
| `diff_feedback` | id, diff_id, ai_category, human_category, operator, created_at | 人工纠正 → 评测样本 |

金额一律 `int64` 分；时间统一 `timestamptz`。

### 5.2 接口契约（proto）

**recon-core**
```proto
CreateTask(CreateTaskReq) returns (CreateTaskRsp);
ListDiffs(ListDiffsReq) returns (ListDiffsRsp);
GetDiff(GetDiffReq) returns (DiffDetail);
SaveClassification(SaveClassificationReq) returns (Empty);
ConfirmDiff(ConfirmDiffReq) returns (Empty);
GetTaskSummary(GetTaskSummaryReq) returns (TaskSummary);
```

**recon-ai**
```proto
ClassifyDiff(ClassifyDiffReq) returns (ClassifyDiffRsp);
ClassifyBatch(ClassifyBatchReq) returns (ClassifyBatchRsp);
```

**recon-bff（HTTP）**
```
POST /api/tasks
GET  /api/tasks/{id}
GET  /api/tasks/{id}/diffs
GET  /api/diffs/{id}
POST /api/diffs/{id}/confirm
GET  /api/tasks/{id}/summary
```

### 5.3 状态机

```
task:  CREATED → PARSING → MATCHING → MATCHED
                                 └──→ FAILED（可重跑）

diff:  PENDING → CLASSIFIED → CONFIRMED
                          └──→ CORRECTED
```

**状态只能单向推进**，每次流转写审计日志（谁、何时、从什么到什么）。

### 5.4 匹配算法（三级）

| 级别 | 规则 | 结果标记 |
|---|---|---|
| **L1 精确** | 渠道 `out_trade_no` ↔ 系统 `pay_order_no`，且金额相等 | `exact` |
| **L2 模糊** | 单号缺失时：金额相等 + 时间差 ≤ 1 天 + 窗口内唯一候选 | `fuzzy` |
| **L3 剩余** | 未匹配 → 差异（渠道无系统 / 系统无渠道 / 金额不符） | `none` |

L2 必须要求「唯一候选」，否则宁可判为差异，**不准猜**——这是财务场景的底线。

### 5.5 AI 设计

**输入**：差异类型、两侧关键字段（单号、金额、手续费、时间、状态）、金额差、时间差。

**输出（JSON Schema 强约束）**
```json
{
  "category": "cross_day | fee_diff | refund_unsync | missing_in_system | missing_in_channel | duplicate",
  "confidence": 0.0,
  "reason": "≤200 字",
  "evidence": ["字段名1", "字段名2"],
  "suggestion": "confirm | investigate | ignore"
}
```

**四条硬约束**
1. `evidence` 只能引用输入里存在的字段名（白名单校验），杜绝编造；
2. **金额、条数、比例一律由代码计算**，模型只做分类与措辞；
3. `temperature=0`，同一输入结果稳定；命中缓存直接返回（key = 差异字段 hash，TTL 7 天）；
4. 校验失败重试 ≤ 2 次，仍失败 → **规则兜底**（按差异类型直接映射分类），并标记 `fallback=true`。

**成本控制**：懒归因（点开才调）+ 批量分片（≤50）+ 相同输入缓存 + 每日 token 预算告警。

**评测**：30 条标注样本（6 类 × 5），指标 = 分类准确率 / schema 合法率 / 平均耗时；每次改 prompt 必须跑一遍并记录。

### 5.6 异常与降级矩阵

| 故障 | 表现 | 降级策略 | 用户感知 |
|---|---|---|---|
| LLM 超时 | >10s 无响应 | 规则分类兜底 | 显示「规则判定」，可重试 AI |
| LLM 限流 429 | 调用被拒 | 指数退避重试 2 次 → 兜底 | 同上 |
| AI 服务宕机 | gRPC 不可达 | BFF 熔断，归因按钮置灰 | 对账、列表、导出**照常可用** |
| 模型输出非法 | schema 校验失败 | 重试 → 兜底 | 标记 fallback |
| CSV 格式错 | 解析失败 | 返回行号与原因 | 下载错误报告 |
| DB 慢/超时 | 查询 >3s | 分页 + 超时截断 | 提示「数据较多，请筛选」 |
| 重复上传 | 同 task 重复提交 | 幂等键（文件 hash） | 返回已有任务 |

| 上线检查单 | 迁移成功 / 三服务健康 / 冒烟用例通过 / 日志无 ERROR |

## 9. 问题与解决方案库

> 这一节是项目的「经验资产」，也是面试时最能体现深度的地方。每条都按「现象 → 根因 → 方案 → 验证」记录。

| # | 问题 | 根因 | 解决方案（主选 / 备选） | 如何验证 |
|---|---|---|---|---|
| 1 | 两份账单对不齐 | 单号规则不同、金额单位不同（元/分）、时区不同 | **归一化层**：统一转分、统一 UTC、统一单号字段；输出「数据质量报告」 | 构造 100 条脏数据，全部被报告出来 |
| 2 | 模糊匹配错配 | 时间窗太宽，同金额多笔 | 要求**窗口内唯一候选**；不唯一则判差异 | 构造同金额同时段 3 笔，验证不误配 |
| 3 | AI 同一输入结果不同 | 模型非确定性 | `temperature=0` + 缓存 + 固定 prompt 版本 | 同一样本跑 10 次，结果一致 |
| 4 | AI 编造单号/金额 | 模型自由生成 | `evidence` 白名单校验 + 金额由代码算 + schema 校验 | 注入诱导性 prompt，验证被拦截 |
| 5 | AI 超时拖垮接口 | 同步调用模型 | 10s 超时 + 重试 2 次 + 熔断 + 规则兜底 | 断网测试，接口 ≤ 12s 返回 |
| 6 | 成本失控 | 全量归因 | 懒归因 + 缓存 + 批量分片 + 日预算告警 | 2,000 行任务，AI 调用 ≤ 50 次 |
| 7 | 大文件上传阻塞 | 全量读内存 | 流式解析（`encoding/csv` + reader）+ 大小限制 | 传 50MB 文件，内存平稳 |
| 8 | 重复提交产生重复任务 | 前端重复点击/重试 | 幂等键（文件 hash + 用户） | 连点 5 次，只生成 1 个任务 |
| 9 | 任务状态与差异不一致 | 多步写入无事务 | 状态机 + 单事务写 task/diff + 可重跑 | 人为中断，重跑后数据一致 |
| 10 | 三服务联调困难 | 契约不一致 | proto 先行 + `buf lint/breaking` + trace_id 贯穿 | 改字段后编译即报错 |
| 11 | 本地起 etcd 麻烦 | 强依赖服务发现 | 配置开关：本地直连 endpoint，compose 用 discovery | 两种模式都能跑 |
| 12 | 前端跨域 | 前后端分离 | BFF 同源代理（nginx 反代 `/api`） | 生产构建无 CORS 报错 |
| 13 | AI 没有标准答案，无法评测 | 缺标注 | 先用规则生成 gold，再人工校正；双人标注抽检一致性 | 30 条样本，两人一致率 ≥ 90% |
| 14 | 金额精度问题 | 用 float 算钱 | 全链路 int64 分；比例用 decimal 字符串 | 0.1+0.2 类用例全部正确 |
