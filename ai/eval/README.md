# AI 归因评测

## 为什么要有这个目录

没有评测，"AI 效果不错" 就是一句主观判断。这里用 30 条标注样本，把「准不准」变成可复现的数字，并支撑 **prompt 迭代** 与 **消融实验**。

## 怎么跑

```powershell
# 1. 起 AI 服务（模型开启）
pwsh -File .\scripts\dev.ps1

# 2. 跑评测
go run ./cmd/eval -file ai/eval/data/diffs.jsonl -addr 127.0.0.1:9001 -out ai/eval/report-model.md

# 3. 规则基线（消融实验）：用关闭模型的配置重启 AI
#    把 configs/ai-rules.yaml 里的 llm.enable 设为 false 后启动，再跑一次
go run ./cmd/eval -file ai/eval/data/diffs.jsonl -addr 127.0.0.1:9001 -out ai/eval/report-rules.md
```

## 数据集

`data/diffs.jsonl`，30 条，6 类各 5 条：

| 分类 | 构造特征 |
|---|---|
| cross_day | 交易时间在 23:55 ~ 00:12，单边差异 |
| fee_diff | 两侧金额差恰等于 fee 字段 |
| refund_unsync | 系统状态 REFUNDED，备注含"已退款" |
| missing_in_system | 渠道正常交易，系统无记录 |
| missing_in_channel | 系统正常交易，渠道无记录 |
| duplicate | 备注含"重复扣款/二次扣费/同单号多笔" |

每条包含：`diff_type`、`channel`、`system`、`amount_diff`、`time_diff_hours`、`expected`。

## 结果

| 版本 | 准确率 | 说明 |
|---|---|---|
| 规则兜底（模型关闭） | **50.0%**（15/30） | 只能判 3 个「结构清晰」的类别 |
| prompt v1 | **56.7%**（17/30） | 只列分类定义，没有判断优先级 |
| prompt v2 | **100%**（30/30） | 加入 6 步判断优先级后 |

**v1 → v2 的差距全在三类**：`cross_day` 0→100%、`refund_unsync` 0→100%、`duplicate` 40→100%。

原因：v1 只写了"每一类是什么"，模型在单边差异上会直接套用 `missing_in_*`，忽略 `status`、时间边界、备注语义。v2 显式规定「先看退款状态 → 再看时间边界 → 再看重复语义 → …」，命中即停。

## ⚠️ 关于 100% 的重要说明

**这个 100% 有明显的过拟合成分，不能当成真实水平。** 原因：

1. **同一人写了 prompt 判定规则和评测样本** —— 样本是按规则的判定依据构造的（"23:58"对应跨日、"REFUNDED"对应退款），等于把答案写进了题目；
2. **样本模式化** —— 现实中的差异不会这么工整，备注措辞、状态取值、金额组合都更杂乱；
3. **样本量太小** —— 30 条不足以覆盖真实分布，置信区间很宽。

真实环境下的合理预期是 **75%~85%**。要接近这个数字，需要：

- 从真实历史差异里抽样标注（而不是人工构造）；
- 留出 20 条**不参与 prompt 调优**的 hold-out 集；
- 引入"模糊样本"（同一笔既有跨日又疑似手续费）；
- 多人标注并计算一致性（Kappa）。

## 评测指标

| 指标 | 用途 |
|---|---|
| 分类准确率 | 主指标，衡量"判得对不对" |
| 分类别准确率 | 定位是哪一类在拖后腿 |
| 混淆矩阵 | 看系统性混淆（如 cross_day ↔ missing_in_system） |
| 兜底次数 | 模型不可用/输出非法的比例，反映稳定性 |
| 平均延迟 / token | 成本与体验 |

## 结论怎么写进简历

✅ 可以写：

> 建立 30 条标注集的评测流程，通过对比实验把归因准确率从 56.7% 提升到 100%（自建集），并完成规则基线与模型基线的消融对比。

❌ 不要写：

> AI 归因准确率 100%。

前者说明"我会做评测、会迭代"，后者会被追问穿。
